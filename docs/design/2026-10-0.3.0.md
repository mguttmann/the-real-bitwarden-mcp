# Design: 0.3.0 (2026-10)

## Goal

Close the tool-schema and robustness items the 2026-10-27 audit left open
because they needed owner decisions, without breaking any gateway that
pins the tool contract.

## Owner decisions (2026-10-27)

1. **Contract: optional parameters may be added.** No tool, parameter or
   required entry is renamed or removed. The v0.1.1 baseline
   (`tests/fixtures/tool-contract.json`) stays frozen; additions are
   recorded per config and tool in `tests/fixtures/tool-contract-added.json`.
   One rule (`scripts/tool-contract.mjs`) is used by the contract test,
   the stdio probe test and both smoke scripts: names and required lists
   identical, property names the baseline plus exactly the recorded
   additions. A removed baseline property or an unrecorded addition fails.
2. **Response size:** successful tool output above an optional byte
   budget is cut with a marker that says how to page or narrow the query,
   as valid JSON.
3. **Input bounds:** only absurd sizes are rejected, with the limits in
   one place.
4. **Token backoff:** a short pause after repeated failed token requests
   per client, reset by a success.
5. **No live check** against a real Secrets Manager in this release.

## Stage B outcome (decisions 2 to 4)

All values are in `src/limits.ts`; the checks run in `tools/call`
(`src/server.ts`), so every tool, including `bw_raw_request`, the confirm
preview and the generated tools, gets them.

- **Response cut** (`BW_MCP_MAX_RESPONSE_BYTES`, optional): measured in
  UTF-8 bytes of the result text. A JSON result keeps the leading items of
  its largest list (root, a top-level property, or one level below, such
  as `bw_raw_request`'s `body.data`), found by binary search, plus a
  `responseTruncated` marker; a sibling `continuationToken` is removed
  because it would skip the cut items. Other output becomes the marker
  alone. Error results are not cut (upstream error texts already are).
  The list `note` from `BW_MCP_MAX_LIST_RESPONSE_BYTES` stays a hint at its
  own lower threshold and survives a cut. The upstream body is still read
  in full before the cut; a streaming read cap was not built.
- **Input bounds**: strings (and object keys) over the byte limit and
  arrays over the item limit, anywhere in the arguments, are rejected with
  the parameter path and size, never the value, and a warn log line with
  the tool name. Nothing is sent and no preview is built.
- **Token backoff** (`src/http/token-backoff.ts`): one instance per
  `OAuthTokenCache` (self-host, cloud, SM REST) and one for the SM SDK
  login. Concurrent callers sharing one in-flight request count once; a
  timeout counts as a failure (for the SDK login: once per login, see
  stage C); a cached valid token is still used.

## Stage C outcome (backlog)

- **Boolean switches:** `parseBool` also knows `on`/`off`. An empty or
  whitespace-only `BITWARDEN_READ_ONLY` is unset (off); any other
  unrecognised value still turns read-only mode on (fails safe).
- **Pagination at the exact limit:** since 0.2.0 a page that ends exactly
  at `PAGINATION_MAX_ITEMS` stops and returns the next token. Whether that
  next page is empty cannot be told without fetching it (the API sends a
  token either way), so `truncated: true` stays and README says the
  resumed page can be empty. No extra request was added.
- **One deadline per `bws_*` call:** `src/http/sm-sdk-client.ts` runs each
  client method under one `HTTP_TIMEOUT_MS` timer that covers the login
  wait and every SDK call. The read-before-write of `bws_secret_update`
  moved from the tool into `secretUpdate` (omitted `note` or `projectIds`
  are passed as undefined), so both calls share that deadline.
- **Shared SDK login:** a running login is shared by every call until it
  settles, also after a caller timed out on it, so a late success is
  used and no second login runs beside it. A login still running after
  `SM_LOGIN_REUSE_TIMEOUTS` x `HTTP_TIMEOUT_MS` (`src/limits.ts`) is given
  up (the native call cannot be cancelled) and the next call starts a new
  one, subject to the token backoff. The first timeout on a login counts
  one backoff failure; its later failure does not count again.
- **Release recovery:** RELEASING.md, "Recovering a release". The
  `mcp-registry.yml` checkout is the tag for both triggers, validated
  before the checkout, and the tag's `server.json` must already carry the
  tag version instead of being rewritten.
- Repository security settings, rulesets and npm trusted publishing were
  read back with `gh api` (GET only) on 2026-10-27 and their backlog
  items removed; `docs/maintainers/repo-settings.md` holds the state.
